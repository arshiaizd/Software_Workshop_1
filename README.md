### ۱. پوشهٔ `.git` چیست، چه اطلاعاتی در آن ذخیره می‌شود و با چه دستوری ساخته می‌شود؟

پوشهٔ `.git` بخش اصلی و داخلی یک مخزن گیت است. وقتی یک پوشهٔ معمولی را به مخزن گیت تبدیل می‌کنیم، گیت اطلاعات مربوط به تاریخچه و وضعیت پروژه را در این پوشه نگهداری می‌کند.

برخی از مهم‌ترین اطلاعات موجود در `.git` عبارت‌اند از:

- تاریخچهٔ ثبت تغییرات
- شاخه‌ها و اشاره‌گرهای مربوط به آن‌ها
- وضعیت فعلی `HEAD`
- ناحیهٔ آماده‌سازی یا `index`
- تنظیمات محلی مخزن
- اطلاعات مربوط به مخزن‌های راه‌دور
- اشیای داخلی گیت شامل محتوای فایل‌ها، ساختار پوشه‌ها و ثبت تغییرات
- گزارش برخی عملیات‌های انجام‌شده در مخزن

برای ساختن این پوشه و تبدیل یک پوشهٔ معمولی به مخزن گیت از دستور زیر استفاده می‌شود:

```bash
git init
```

پس از اجرای این دستور، پوشهٔ مخفی `.git` ساخته می‌شود و از آن لحظه گیت می‌تواند تغییرات پروژه را دنبال کند.

### ۲. منظور از اتمی بودن در یک ثبت تغییر و یک درخواست ادغام چیست؟

اتمی بودن یعنی یک تغییر تا حد ممکن فقط **یک هدف مشخص و مستقل** داشته باشد.

#### ثبت تغییر اتمی

یک ثبت تغییر اتمی باید فقط یک تغییر منطقی مشخص را انجام دهد. برای مثال بهتر است افزودن قابلیت حذف وظیفه و تغییر کامل ظاهر برنامه در یک ثبت تغییر قرار نگیرند.

نمونهٔ مناسب:

```text
افزودن قابلیت حذف وظیفه
```

در یک ثبت تغییر اتمی:

- تغییرات به یک موضوع مشخص مربوط هستند.
- بررسی آن ساده‌تر است.
- در صورت بروز مشکل، پیدا کردن منشأ خطا آسان‌تر می‌شود.
- بازگرداندن آن تغییر بدون تأثیر زیاد بر بخش‌های دیگر راحت‌تر است.
- تاریخچهٔ پروژه قابل فهم‌تر باقی می‌ماند.

#### درخواست ادغام اتمی

درخواست ادغام اتمی نیز باید یک هدف مشخص داشته باشد. برای مثال یک درخواست ادغام می‌تواند فقط مربوط به «اضافه کردن رابط کاربری واکنش‌گرا» باشد.

یک درخواست ادغام ممکن است چند ثبت تغییر داشته باشد، اما همهٔ آن ثبت‌ها باید در راستای یک قابلیت یا هدف مشخص باشند.

در نتیجه، اتمی بودن به معنی کوچک بودن صرف نیست؛ بلکه به معنی **تمرکز هر تغییر بر یک مسئولیت مشخص و منطقی** است.

### ۳. تفاوت دستورهای `fetch`، `pull`، `merge`، `rebase` و `cherry-pick` چیست؟

#### دستور `fetch`

این دستور تغییرات جدید را از مخزن راه‌دور دریافت می‌کند، اما آن‌ها را مستقیماً وارد شاخهٔ فعلی نمی‌کند.

```bash
git fetch origin
```

بعد از اجرای این دستور، اطلاعات شاخه‌های راه‌دور به‌روزرسانی می‌شود، اما فایل‌های شاخهٔ فعلی ما تغییر نمی‌کنند.

بنابراین `fetch` برای مشاهده و دریافت امن تغییرات راه‌دور مناسب است.

---

#### دستور `pull`

دستور `pull` تغییرات را از مخزن راه‌دور دریافت کرده و سپس آن‌ها را با شاخهٔ فعلی ترکیب می‌کند.

به‌صورت مفهومی می‌توان گفت:

```text
pull = fetch + ادغام
```

در حالت معمول، ادغام توسط `merge` انجام می‌شود؛ البته می‌توان گیت را تنظیم کرد که بعد از دریافت تغییرات از `rebase` استفاده کند.

مثال:

```bash
git pull origin main
```

---

#### دستور `merge`

دستور `merge` تاریخچهٔ دو شاخه را با یکدیگر ترکیب می‌کند.

```bash
git merge feature/example
```

اگر تغییرات دو شاخه با یکدیگر ناسازگار باشند، ممکن است تعارض ایجاد شود و لازم باشد آن را به‌صورت دستی حل کنیم.

یکی از ویژگی‌های مهم `merge` این است که تاریخچهٔ واقعی شاخه‌ها حفظ می‌شود و در بسیاری از موارد یک ثبت ادغام با دو والد ایجاد می‌شود.

---

#### دستور `rebase`

دستور `rebase` ثبت تغییرات یک شاخه را برداشته و آن‌ها را روی یک نقطهٔ پایهٔ جدید دوباره اعمال می‌کند.

در نتیجه تاریخچه معمولاً خطی‌تر می‌شود.

برای مثال:

```bash
git rebase main
```

تفاوت مهم آن با `merge` این است که `rebase` ثبت‌های تغییر را دوباره ایجاد می‌کند و در نتیجه شناسهٔ آن‌ها تغییر می‌کند.

به همین دلیل استفاده از `rebase` روی شاخه‌هایی که قبلاً به اشتراک گذاشته شده‌اند باید با احتیاط انجام شود.

---

#### دستور `cherry-pick`

این دستور برای برداشتن یک یا چند ثبت تغییر مشخص از یک شاخه و اعمال آن روی شاخهٔ فعلی استفاده می‌شود.

برای مثال:

```bash
git cherry-pick abc1234
```

در این حالت فقط همان تغییر انتخاب‌شده وارد شاخهٔ فعلی می‌شود و نیازی نیست کل شاخه را ادغام کنیم.

در نتیجه:

- `fetch` فقط تغییرات راه‌دور را دریافت می‌کند.
- `pull` تغییرات را دریافت و سپس با شاخهٔ فعلی ترکیب می‌کند.
- `merge` تاریخچهٔ دو شاخه را با هم ترکیب می‌کند.
- `rebase` ثبت‌های یک شاخه را روی پایهٔ جدید دوباره اعمال می‌کند.
- `cherry-pick` فقط ثبت‌های انتخاب‌شده را روی شاخهٔ فعلی اعمال می‌کند.

---

### ۴. تفاوت دستورهای `reset`، `revert`، `restore`، `switch` و `checkout` چیست؟

#### دستور `reset`

دستور `reset` برای جابه‌جا کردن اشاره‌گر شاخه یا تغییر وضعیت ناحیهٔ آماده‌سازی و در برخی حالت‌ها فایل‌های پوشهٔ کاری استفاده می‌شود.

حالت‌های معروف آن عبارت‌اند از:

```bash
git reset --soft
git reset --mixed
git reset --hard
```

حالت `--hard` می‌تواند تغییرات فایل‌های کاری را نیز حذف کند؛ بنابراین باید با احتیاط از آن استفاده شود.

`reset` بیشتر برای اصلاح تاریخچهٔ محلی مناسب است و استفادهٔ نادرست از آن روی تاریخچهٔ اشتراکی ممکن است مشکل ایجاد کند.

---

#### دستور `revert`

دستور `revert` برخلاف `reset` تاریخچهٔ قبلی را حذف نمی‌کند.

این دستور یک ثبت تغییر جدید ایجاد می‌کند که اثر یک ثبت تغییر قبلی را خنثی می‌کند.

```bash
git revert abc1234
```

به همین دلیل برای شاخه‌های اشتراکی مانند `main` معمولاً امن‌تر از بازنویسی تاریخچه با `reset` است.

---

#### دستور `restore`

دستور `restore` برای بازگرداندن محتوای فایل‌ها استفاده می‌شود.

برای مثال:

```bash
git restore file.txt
```

می‌تواند تغییرات ثبت‌نشدهٔ یک فایل را کنار بگذارد.

همچنین می‌توان از آن برای تغییر وضعیت فایل در ناحیهٔ آماده‌سازی استفاده کرد.

```bash
git restore --staged file.txt
```

---

#### دستور `switch`

دستور `switch` برای جابه‌جایی بین شاخه‌ها طراحی شده است.

```bash
git switch main
```

همچنین می‌توان با آن شاخهٔ جدید ساخت:

```bash
git switch -c feature/example
```

---

#### دستور `checkout`

`checkout` دستور قدیمی‌تر و چندمنظورهٔ گیت است که هم برای تغییر شاخه و هم برای بازگرداندن فایل‌ها استفاده می‌شد.

برای مثال:

```bash
git checkout main
```

یا در کاربردهای قدیمی برای بازگرداندن یک فایل.

به دلیل چندمنظوره بودن `checkout`، در نسخه‌های جدید گیت دو دستور واضح‌تر معرفی شدند:

- `switch` برای کار با شاخه‌ها
- `restore` برای بازگرداندن فایل‌ها

در نتیجه می‌توان گفت:

- `reset` اشاره‌گرها و وضعیت ناحیهٔ آماده‌سازی یا فایل‌ها را تغییر می‌دهد.
- `revert` با ساخت یک ثبت جدید، اثر ثبت قبلی را خنثی می‌کند.
- `restore` برای بازگرداندن فایل‌ها یا وضعیت آن‌ها استفاده می‌شود.
- `switch` برای جابه‌جایی بین شاخه‌ها است.
- `checkout` دستور قدیمی‌تر و چندمنظوره‌ای است که بخشی از وظایف `switch` و `restore` را انجام می‌دهد.

---

### ۵. منظور از ناحیهٔ آماده‌سازی یا `index` چیست و دستور `stash` چه کاری انجام می‌دهد؟

#### ناحیهٔ آماده‌سازی

ناحیهٔ آماده‌سازی یک فضای میانی بین فایل‌های در حال ویرایش و ثبت تغییر نهایی است.

چرخهٔ معمول کار به شکل زیر است:

```text
پوشهٔ کاری
↓
ناحیهٔ آماده‌سازی
↓
ثبت تغییر
```

وقتی یک فایل را تغییر می‌دهیم، تغییر آن ابتدا فقط در پوشهٔ کاری قرار دارد.

با دستور زیر:

```bash
git add file.txt
```

نسخهٔ موردنظر فایل وارد ناحیهٔ آماده‌سازی می‌شود.

سپس:

```bash
git commit
```

از اطلاعات موجود در ناحیهٔ آماده‌سازی برای ساخت ثبت تغییر بعدی استفاده می‌کند.

بنابراین ناحیهٔ آماده‌سازی به ما اجازه می‌دهد مشخص کنیم دقیقاً کدام تغییرات در ثبت بعدی قرار بگیرند.

`index` نام داخلی همین ناحیه در گیت است.

---

#### دستور `stash`

دستور `stash` برای کنار گذاشتن موقت تغییرات ثبت‌نشده استفاده می‌شود.

فرض کنید روی یک قابلیت کار می‌کنیم، اما هنوز آمادهٔ ثبت تغییر نیست و لازم است موقتاً به شاخهٔ دیگری برویم.

می‌توانیم اجرا کنیم:

```bash
git stash
```

گیت تغییرات را موقتاً ذخیره می‌کند و پوشهٔ کاری را به وضعیت تمیز نزدیک می‌کند.

برای مشاهدهٔ موارد ذخیره‌شده می‌توان از دستور زیر استفاده کرد:

```bash
git stash list
```

برای بازگرداندن تغییرات:

```bash
git stash apply
```

و برای بازگرداندن تغییرات و حذف آن‌ها از فهرست ذخیره‌ها:

```bash
git stash pop
```

بنابراین `stash` یک محل موقت برای نگهداری تغییراتی است که هنوز نمی‌خواهیم آن‌ها را به‌صورت ثبت تغییر دائمی ذخیره کنیم.

---

### ۶. مفهوم تصویر لحظه‌ای چیست و چه ارتباطی با ثبت تغییر دارد؟

گیت را می‌توان سیستمی دانست که در هر ثبت تغییر، یک **تصویر لحظه‌ای از وضعیت پروژه** نگهداری می‌کند.

تصویر لحظه‌ای یعنی وضعیت فایل‌ها و پوشه‌های پروژه در یک لحظهٔ مشخص.

فرض کنیم پروژه در یک لحظه شامل سه فایل باشد:

```text
index.html
style.css
app.js
```

بعد از انجام تغییرات و ثبت آن‌ها، گیت وضعیت آن لحظه از این فایل‌ها را به‌عنوان یک تصویر از پروژه در تاریخچه نگهداری می‌کند.

ثبت تغییر فقط مجموعه‌ای از خطوط تغییرکرده نیست؛ بلکه به یک تصویر از ساختار کامل پروژه اشاره می‌کند.

هر ثبت تغییر علاوه بر تصویر پروژه، اطلاعات دیگری نیز دارد، مانند:

- نویسنده
- زمان ثبت
- پیام ثبت تغییر
- والد یا والدهای ثبت تغییر
- اشاره به ساختار فایل‌های پروژه

ثبت تغییر بعدی نیز تصویر جدیدی ایجاد می‌کند و به ثبت قبلی اشاره دارد.

به همین دلیل تاریخچهٔ گیت را می‌توان به شکل زنجیره‌ای از تصاویر مختلف پروژه در طول زمان در نظر گرفت.

البته برای جلوگیری از ذخیرهٔ چندبارهٔ اطلاعات یکسان، گیت داده‌های تکراری را به شکل بهینه مدیریت می‌کند و اشیای یکسان را دوباره ذخیره نمی‌کند.

در نتیجه، ارتباط تصویر لحظه‌ای و ثبت تغییر این است که **هر ثبت تغییر نمایانگر یک وضعیت مشخص و قابل بازیابی از پروژه در یک لحظه از تاریخچه است**.

---

### ۷. تفاوت مخزن محلی و مخزن راه‌دور چیست؟

#### مخزن محلی

مخزن محلی نسخه‌ای از مخزن است که روی رایانهٔ توسعه‌دهنده قرار دارد.

در مخزن محلی می‌توان:

- فایل‌ها را ویرایش کرد.
- شاخه ساخت.
- ثبت تغییر ایجاد کرد.
- تاریخچه را مشاهده کرد.
- بین شاخه‌ها جابه‌جا شد.
- بدون اتصال به اینترنت روی پروژه کار کرد.

پوشهٔ `.git` نیز در مخزن محلی اطلاعات تاریخچه و وضعیت گیت را نگهداری می‌کند.

---

#### مخزن راه‌دور

مخزن راه‌دور نسخه‌ای از مخزن است که روی یک سامانهٔ دیگر، مانند گیت‌هاب، نگهداری می‌شود.

هدف اصلی آن اشتراک‌گذاری پروژه میان اعضای گروه، پشتیبان‌گیری از تاریخچه و هماهنگ کردن تغییرات است.

برای مشاهدهٔ مخزن‌های راه‌دور تعریف‌شده می‌توان از دستور زیر استفاده کرد:

```bash
git remote -v
```

معمولاً مخزن راه‌دور اصلی با نام `origin` شناخته می‌شود.

برای ارسال تغییرات محلی به مخزن راه‌دور از دستور زیر استفاده می‌شود:

```bash
git push
```

برای دریافت اطلاعات جدید از مخزن راه‌دور:

```bash
git fetch
```

و برای دریافت و ادغام تغییرات:

```bash
git pull
```

بنابراین:

| مخزن محلی | مخزن راه‌دور |
|---|---|
| روی رایانهٔ توسعه‌دهنده قرار دارد | روی یک سرویس یا سرور دیگر قرار دارد |
| امکان کار بدون اینترنت را فراهم می‌کند | برای اشتراک‌گذاری و همکاری گروهی استفاده می‌شود |
| ثبت تغییر و شاخه‌های محلی در آن وجود دارند | نسخهٔ مشترک شاخه‌ها و ثبت‌های گروه را نگهداری می‌کند |
| تغییرات با `push` ارسال می‌شوند | تغییرات آن با `fetch` یا `pull` دریافت می‌شوند |

در یک پروژهٔ گروهی، هر عضو مخزن محلی خودش را دارد و همهٔ اعضا از طریق مخزن راه‌دور مشترک تغییرات خود را با یکدیگر هماهنگ می‌کنند.
